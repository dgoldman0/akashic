# akashic-sha512 — Checked Hardware SHA-512

`math/sha512.f` is the Akashic one-shot boundary for the Megapad-64 BIOS
SHA-512 engine. SHA-512 compression, padding, per-core context storage,
digest staging, and erasure are hardware/BIOS responsibilities. Akashic adds
public span policy, scoped ownership, status normalization, and digest
utilities; it contains no software round engine or mutable SHA-512 schedule.

```forth
REQUIRE math/sha512.f
```

## API

```forth
SHA512-LEN           ( -- 64 )
SHA512-HEX-LEN       ( -- 128 )
SHA512-STATUS-VALID? ( status -- flag )
SHA512-CALLER-SPAN-STATUS
  ( address length -- status )

SHA512-HASH
  ( src len dst -- status )

SHA512-HASH-2
  ( a1 u1 a2 u2 dst -- status )

SHA512-HASH-3
  ( a1 u1 a2 u2 a3 u3 dst -- status )

SHA512->HEX     ( digest destination -- 128 )
SHA512-.        ( digest -- )
SHA512-COMPARE  ( first second -- equal? )
```

The multi-span forms hash the exact byte concatenation without allocating a
concatenation buffer. Input spans may overlap one another.

There is deliberately no public streaming API. A caller-spanning
INIT/UPDATE/FINAL sequence would expose a live BIOS context across arbitrary
caller work, exceptions, and recursive hashes. Each public call instead owns
one complete transaction.

`SHA512-CALLER-SPAN-STATUS` is the reusable, nonmutating caller-memory
boundary. It returns `0`/`OK` for an empty or admitted span, `2`/`RANGE`
when the complete span is not inside one BIOS-advertised physical window,
`3`/`ALIAS` for the SHA-512 guard, shared crypto-ACC storage, or either
algorithm's complete all-core BIOS context arena, and `5`/`INVALID` for
negative, null nonempty, or wrapping geometry. A caught exception or an
undocumented BIOS result is normalized to `6`/`CRYPTO`; this word never
returns `STATE` or `LENGTH-OVERFLOW`.

## Status values

| Status | Meaning |
|---|---|
| `SHA512-S-OK` | The 64-byte digest was published. |
| `SHA512-S-STATE` | The checked BIOS context was not in the required state. |
| `SHA512-S-RANGE` | A span is outside one BIOS-advertised physical window. |
| `SHA512-S-ALIAS` | An input/output pair or caller span/reserved crypto region overlaps, or a BIOS context arena was addressed. |
| `SHA512-S-LENGTH-OVERFLOW` | The SHA-512 128-bit bit-length calculation overflowed. |
| `SHA512-S-INVALID` | Public geometry is negative, null when nonempty, or wrapping. |
| `SHA512-S-CRYPTO` | An unexpected pre-publication exception or invalid BIOS status occurred. |

`SHA512-STATUS-VALID?` accepts exactly the inclusive range from
`SHA512-S-OK` through `SHA512-S-CRYPTO`.

Every returned nonzero hash status leaves all 64 destination bytes
unchanged. Before claiming either crypto resource or issuing `SHA512-INIT`,
the library applies `SHA512-CALLER-SPAN-STATUS` to every input and to the
fixed-size destination, then checks input/output overlap. A zero-length
input is valid and may use address zero; a nonempty input and the destination
must be nonnull and nonwrapping. The pure BIOS qualification includes the
calling core's currently active context, so even that alias returns before
INIT without disturbing the live context. The local guard and crypto-ACC
regions are also rejected before acquisition because acquisition or cleanup
would mutate them.

## Ownership and cleanup

An admitted operation follows this lock and execution order:

```text
CRYPTO-ACC transaction
  -> SHA-512 blocking operation guard
    -> BIOS SHA512-INIT
    -> BIOS SHA512-UPDATE (one to three times)
    -> BIOS SHA512-FINAL
```

The shared accumulator transaction makes SHA-512 composable with the Field
ALU and other EXT.CRYPTO users. The algorithm guard keeps the logical
INIT/UPDATE*/FINAL sequence intact across task switches. BIOS UPDATE and
FINAL defensively repeat physical-window and hidden-context checks before
reading or publishing caller memory.

Every admitted path that fails before successful publication invokes the
idempotent `SHA512-CLEAR` operation while ownership is retained. Successful
FINAL already erases and releases its BIOS context; no post-success CLEAR is
issued.

INIT and UPDATE execute behind a pre-publication `CATCH`, allowing an
unexpected exception to become `SHA512-S-CRYPTO` without weakening the
destination guarantee. FINAL is caught separately. Forth `CATCH` cannot
establish whether a throwing FINAL published before throwing, so that path
performs CLEAR and guard release and then rethrows. It is not converted into
a returned failure.

## Digest utilities

`SHA512->HEX` writes 128 lowercase hexadecimal characters and returns 128.
`SHA512-.` prints that representation. `SHA512-COMPARE` examines all 64
bytes without an early exit.

```forth
CREATE message 3 ALLOT
97 message C!  98 message 1+ C!  99 message 2 + C!
CREATE digest SHA512-LEN ALLOT

message 3 digest SHA512-HASH
DUP IF
    \ digest was not changed
    THROW
THEN
DROP
digest SHA512-.  \ ddaf35a1...
```

Ed25519 is the principal current consumer: key generation uses the one-span
form, signing uses the two- and three-span forms, and verification uses the
three-span form.
